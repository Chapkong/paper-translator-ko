# 논문 번역기 (paper-translator-ko)

영어 학술 논문(PDF·DOCX)을 **한국어로 완역**하는 로컬 파이프라인이다. 요약하지 않는다. 그림·표·연구모형은 번역하지 않고 원문 그대로 이미지로 넣는다.

브라우저에 PDF를 끌어다 놓으면 추출 → 용어표 → 번역 → 검수 → 통독 → 검증까지 자동으로 돌고, 그림이 박힌 HTML 한 파일이 나온다.

## 무엇이 다른가

번역 품질보다 **원문이 온전히 넘어왔는지**를 먼저 본다. 2단 조판 저널 PDF는 텍스트를 그냥 뽑으면 좌우 단이 섞이고 문장이 중간에서 끊기는데, 그 상태로 번역하면 결과물을 쓸 수 없다.

실측 (Peteraf 1993, SMJ, JSTOR 2단 스캔본 14쪽):

| 항목 | 일반적인 PDF 추출 | 이 도구 |
|---|---|---|
| 문자 보존율 | 0.686 | 1.006 |
| 문장이 끊긴 문단 | 90.3% | 1.4% |
| 머리말·바닥글 잔존 | 14회 | 0회 |
| 각주 | 본문에 섞임 | 25개 분리·번역 |

추출이 기준(보존율 0.97, 잘린 문단 0.05)에 못 미치면 **번역을 시작하지 않고 멈춘다.** 깨진 원문을 번역해봐야 토큰만 쓰고 결과도 못 쓰기 때문이다.

## 요구사항

| 필요한 것 | 용도 |
|---|---|
| Python 3.10+ | 파이프라인 스크립트 |
| [Claude Code](https://claude.com/claude-code) CLI (로그인 상태) | 번역·검수 에이전트를 돌린다 |
| Node.js (npx) | 추출 후보 중 하나인 KorDocAI CLI를 부른다 (선택 — 없으면 자체 경로만 쓴다) |

번역은 Claude 구독의 사용량을 쓴다. 별도 API 키는 필요 없다.

## 설치

```bash
git clone https://github.com/Chapkong/paper-translator-ko.git
cd paper-translator-ko
pip install -r requirements.txt
python scripts/selftest.py        # 15개 자체 테스트가 모두 통과하면 준비 완료
```

## 사용법

```bash
python app.py            # Windows에서는 논문번역기.bat 더블클릭
```

브라우저에서 `http://localhost:8765`가 열린다. PDF를 끌어다 놓으면 번역이 시작되고, 끝나면 "번역본 보기"로 HTML을 연다.

논문 1편에 걸리는 시간은 분량에 비례한다. 14쪽·5만 자 논문이 약 40분, 35쪽·13만 자 논문이 1시간 30분 안팎이다. 대부분이 번역·검수에 쓰는 시간이라 추출을 아무리 빠르게 해도 줄지 않는다.

Claude Code 안에서 직접 쓸 수도 있다.

```
/translate input/paper.pdf
```

## 어떻게 도는가

| 단계 | 담당 | 하는 일 |
|---|---|---|
| 1 | `extract.py` | 추출 후보 3종을 모두 돌려 점수가 가장 좋은 것을 고른다. **미달이면 중단** |
| 2 | `chunk.py` | 헤딩 기준 분할(약 6,000자) |
| 3 | `glossary-builder` | 용어 대응표 작성 — 청크를 병렬 번역해도 용어가 흔들리지 않게 |
| 4 | `translator` ×N | 청크별 완역(병렬) |
| 5 | `verify.py` | 기계 검증 — 이미지 실존·숫자·인용·문단 수·미번역 각주 |
| 6 | `reviewer` ×N | 청크별 원문 대조 검수 |
| 7 | `assemble.py` | 병합 + 용어표 부록 |
| 8 | `final-reviewer` | 전문 통독 — 청크 경계 흐름, 용어 일관성, 역어 적절성 |
| 9 | `to_html.py` | 그림을 base64로 박은 단일 HTML |
| 10 | `final_check.py` | **기계 최종 검증** — 결과물을 직접 세어 표로 내놓는다 |
| 11 | `output-verifier` | 결과물 판정. 기계 검증과 어긋나면 기계 쪽을 따른다 |

**파일을 옮기고 세는 일은 스크립트가, 문장을 쓰는 일은 에이전트가 한다.** 이 경계를 넘지 않는 것이 설계 원칙이다.

검증이 여러 겹인 데는 이유가 있다. 개발 중 첫 실행은 파이프라인이 "ALL PASS"를 보고했지만 원문의 3분의 1이 없었고, 두 번째 실행은 각주 25개 중 17개가 영어로 남았는데도 통과했다. 판정하는 주체와 판정받는 주체가 같으면 이런 일이 반복된다. 그래서 `final_check.py`가 에이전트 선언과 무관하게 결과물을 직접 센다.

## 그림·표 처리

스캔본 PDF는 그림이 페이지 이미지의 일부라 따로 뽑을 수 없고, 그림 안 글자만 텍스트로 남아 본문을 더럽힌다(`p S2 ~~ ~ ~~~~~AC AC`). 그래서 캡션을 기준으로 **페이지 영역을 200dpi로 잘라 이미지로 넣고**, 그 영역의 텍스트는 본문에서 뺀다. 원문 모양이 살고 잔재도 함께 사라진다.

표 캡션은 표 위에, 그림 캡션은 그림 아래에 붙는다는 조판 관행을 이용해 자를 방향을 정한다. 애매하면 자르지 않는다 — 잘못 자르면 본문이 이미지 속으로 사라져 번역에서 빠지기 때문이다.

## 규칙 바꾸기

동작이 마음에 안 들면 [`명령서.md`](명령서.md) 한 곳만 보면 된다. 임계값, 각주·그림 처리 방침, 통독 단계의 자동/확인 분류가 모두 거기 있고, 어느 파일의 어느 상수를 고쳐야 하는지도 적혀 있다.

## 한계

- 수식 OCR과 스캔본(텍스트 레이어가 없는 PDF) OCR은 꺼져 있다. KorDocAI 옵션(`--formula-ocr`, `--ocr`)으로 켤 수 있다.
- 3단 이상 복잡 조판은 검증하지 않았다. 게이트가 미달로 잡아 멈출 것이다.
- 캡션이 없는 그림은 잘라내지 못한다.
